# Sessions and context management

`cortex-session` stores conversations. `cortex-agent` decides what part of a stored conversation is sent to the model. This page covers both, because one rule shapes them together: **history that has been sent to a model is never edited**.

## Why append-only

Two facts from the providers (sources in the research notes; re-check when building):

- **Prompt caches match on prefixes.** Any byte that changes early in a request makes everything after it a cache miss, which costs money and adds latency.
- **Reasoning is bound to the history that produced it.** Anthropic's current models reject a request, or drop the reasoning, when the system prompt, the tool list or any earlier message has changed since a reasoning block was produced. OpenAI's newer models drop reasoning in the same case. Losing reasoning between tool calls makes an agent worse and more expensive.

So the design never does the things harnesses commonly do to save tokens: trimming old tool results in place, rewriting the system prompt mid-session, injecting a reminder and deleting it later, or swapping the tool list. Each has an append-only replacement here.

| Instead of | Cortex-Harness does |
|---|---|
| Editing the system prompt mid-session | Appends a notice message. |
| Changing the tool list mid-session | Keeps the list fixed for the context epoch. MCP and extension tools are reached through a fixed pair of tools ([05-tools.md](05-tools.md)), so a tool added mid-session works at once without touching the list. |
| A per-turn reminder that is deleted next turn | Appends it and leaves it. |
| Trimming old tool results in place | Bounds every result when it is created ([05-tools.md](05-tools.md)), and reclaims space only at compaction. |
| Summarising old turns while replaying newer ones unchanged | Starts a new context epoch (below). |

## Context epochs

A session is a sequence of epochs.

```
epoch 1                                   epoch 2
┌──────────────────────────────────┐      ┌──────────────────────────────────────┐
│ system prompt + tools (frozen)   │      │ system prompt + tools (rebuilt)      │
│ user, assistant, tool results …  │ ───► │ summary of epoch 1 + carried state   │
│ (append-only)                    │      │ user, assistant, tool results …      │
└──────────────────────────────────┘      └──────────────────────────────────────┘
          compaction, or a change of model, protocol or tool set
```

- Within an epoch, each request's prefix is byte-identical to the previous request's. A debug-build check and tests enforce it ([04-providers.md](04-providers.md)).
- A new epoch is the only place where the system prompt and tool list may change, where project instructions are re-read in full, and where old content is dropped.
- Epoch boundaries never fall inside a tool round.

**As built in step 15** (`cortex-agent`, `context` and `turn::epochs`). An epoch begins, and is an `epoch` entry in the log, for one of four reasons:

| Reason | When | The prompt and the tools | The history |
|---|---|---|---|
| `start` | The session's first turn. | Built. | What there is. |
| `resume` | A session read again (a resume, a rewind, a store failure) whose prompt the harness would now build otherwise: its tools changed, the prompt but for its instruction files changed (the epoch's `base` hash), or the log holds the prompt masked by the secret filter. | Built again. | Goes on, every reasoning block in it dropped. |
| `model` | Before a request, when the main role's provider, protocol, model or reasoning level is not the epoch's. | **Kept as they are**, so that the reasoning in the history stays valid and the provider's replay rule decides what the new model reads ([04-providers.md](04-providers.md), "The conversation model"). | Goes on unchanged. |
| `compaction` | A compaction (below). | Built again, the instruction files read again. | A summary, and what it did not cover. |

- **One rule for reasoning:** an assistant message is sent with its reasoning and the provider's own blocks only while every epoch since the one it was produced in has kept that prefix (system prompt and tools). Once an epoch with another prefix begins, it is sent without them, as a message from another provider would be, and it stays so if a later epoch returns to its prefix: what came between changed the history before it. `Context::load` applies the rule to the log by the epochs recorded since each item, and rebuilds each summary's history as the live session replayed it, so a history read again is the history built live, byte for byte. Tests hold it to that across reloads (`a_history_read_again_is_the_one_built_live`), over two summaries in a row, and over a prompt that changes and changes back (`cortex-agent`'s `context::tests`).
- **Every new epoch is a new epoch of the table of seen files** (`Session::new_file_epoch`), the one place a rewind's reload starts one too: the next read of any file is whole, and the snapshots stay.
- **A resumed session goes on in its epoch** when the prompt the harness would build is the stored one but for its instruction files: what changed in those is told as a notice, and reasoning stays valid. It does not start a new epoch because the provider's cache may have expired: that would drop the history's reasoning for nothing the cache could have kept. A session read again on a later day is told the date in a notice.

## On-disk layout

```
<data dir>/sessions/<project key>/
    index.json                       rebuildable cache for listing sessions
    index.lock                       keeps two writers of the index apart
    <session id>/
        log.jsonl                    the session: append-only, the source of truth
        lock                         held by the one process that writes the log
        log.cut-<offset>             the bytes of a last line a crash cut off, set aside
        artifacts/<id>.<ext>         full tool outputs and other large content
        checkpoints/<hash>           file contents, filed under their hash
```

- The data directory follows the platform convention (`$XDG_DATA_HOME/cortex-harness` on Linux, `%LOCALAPPDATA%\cortex-harness` on Windows) and is configurable (`session.data_dir`). `cortex-session` takes every path as an input; `cortex-config` says where the data directory is.
- **The project key** is `AbsPath::project_key` in `cortex-base`: the first 32 lowercase hexadecimal digits (128 bits) of the `ContentHash` (SHA-256) of the workspace's **resolved** root, as the file system spells it. Sessions, stored approvals, project trust, statistics and the project's knowledge are all filed under it, so it is one definition beside the path code, and two projects must never share one: 128 bits of a hash nobody can make collide put a collision between two real workspaces out of reach, and keep paths short on Windows. It has no readable prefix, so a directory listing does not show the names of a user's projects. Decided in step 8.
  - **On Windows the names are hashed in the case stored on disk, not folded** (the owner's decision in step 12). The resolver has already put every name of the root in its stored case, so one folder reached under any casing has one key. And two folders that differ only in case, which NTFS allows inside a directory marked case-sensitive, have two: folded, `App` and `app` would share their sessions, approvals and trust. Only the drive letter, or a share's server and name, is folded, because it has no spelling on disk. Both halves are tested on the Windows runner, the second in a real case-sensitive directory.
- Session ids are time-ordered, so sorting by id sorts by creation time. An id is `s_` and 22 characters: ten for the creation time in milliseconds and twelve random ones, in a 32-character alphabet of digits and lowercase letters that sorts as the numbers do (`cortex-base`, `id`). Lowercase only, because the id is a directory name and Windows ignores case. Ids made by one process never go backwards, even within a millisecond or after the clock is set back.
- **Every file and directory is created owner-only**, through `cortex_base::private` ([decision 0029](../decisions/0029-owner-only-files-on-windows.md)): a new file with `private::create_new`, a rewritten one with `write_atomic` and `owner_only`, every time. A file is never created first and protected afterwards. On a file system that keeps no permissions (FAT, exFAT, some network shares) the session is still written, and opening it reports which of its files are not private.
- **Artifacts** are named by counted ids, `a_0001`, the form the model is told; a new artifact takes the next number after any in the directory. It is written under `<id>.part` and renamed when it is finished, so a half-written artifact never has an artifact's name.
- **The checkpoint store** is content-addressed: a file's content filed under its hash, written once, and checked against the hash when it is read. The checkpoints behind undo and the file versions behind changed-only re-reads ([05-tools.md](05-tools.md), "The content store") are the same thing, so they share it.
- **What the store reads of a file** (`DiskStore::put_file`): a regular file only. A link is never followed, and a device, a FIFO or a directory is refused, so nothing outside the workspace is copied in through a link and no read waits on a pipe or runs forever on `/dev/zero`. Since step 10 the open itself is the check (`cortex_base::open_regular`): the path is not looked at and then opened, so a file that is swapped for a link or a FIFO between the two is neither followed nor waited on ([05-tools.md](05-tools.md), "What resolution does not promise"). The read is bounded by the length the file had when it was opened, not by the size limit: up to the limit is copied, and the hash and size cover that whole length, so a file over the limit is still known by its hash. A file that grows while it is read is recorded as it was when it was opened. Content from elsewhere, such as a file's earlier version read from git, goes in through `DiskStore::put_stream` under the same limit. Looking at what a file is now, when a round ends or a rewind is planned, reads the same way; something at the path that is not a regular file is never opened, and is known by a hash of what it is (its kind, and for a link the text it holds), with size 0 and nothing kept, so that a rewind can tell whether it is as the harness left it.

JSONL files were chosen over a database. The comparison and the measured cost of bundling SQLite are in [decision 0006](../decisions/0006-session-storage.md).

## The log

One JSON object per line. Every entry has the same envelope.

```json
{"v":1,"id":"e_0007","parent":"e_0006","ts":"2026-11-12T10:15:02Z","turn":"t_3","kind":"assistant", "...": "kind-specific fields"}
```

- `v` is the format version the line was written in: 1.
- `id` counts up within the session. `e_0000` is the first line, the `session` entry, which is the root of the tree; every other entry is `e_0001` onwards.
- `parent` makes the log a tree. Rewinding to an earlier point and continuing adds a sibling; nothing is removed.
- **Session records.** An entry with `parent: null` after the first line is outside the conversation tree: `base`, `lease`, `meta`, `usage`, `outcome`, `escalation`, `decision`, and `ext`. They belong to the session, not to a branch, so a rewind never hides the base state or a lease.
- **The active position is the last tree entry in the file**, and the active branch is the path from it to the root. A rewind, an undo and a switch of branch each append a `rewind` entry whose parent is the entry moved to, so the position survives a restart without anything being edited.
- `turn`, when present, is the turn the entry was made in (`t_N`). Undo finds a turn's start, its checkpoints and its outcomes by it.
- `redacted`, when present and not `false`, says that what the line holds is not what the entry held: the secret filter masked something in it, or the core altered it for storage ("Secrets in sessions", below). Added in step 13a. A build from before it skips the field, as it skips any field it does not know.

| Kind | Content | Sent to the model |
|---|---|---|
| `session` | First line: `session` (the id), `workspace` (the root, with `/`), `harness` (the version that created it), `forked_from` (`{session, entry}`) if forked. The creation time is its `ts`. | no |
| `base` | The workspace's starting state (below). Taken in the background after the session starts. It is what makes a session replayable ([16-run-engine.md](16-run-engine.md)). A record. | no |
| `epoch` | Start of a context epoch: `provider`, `protocol`, `model`, `effort`, the `system` prompt text, the `tools` definitions (`name`, `description`, `parameters`), and a `hash` of both, taken before the secret filter. Since step 15 also `reason` (`start`, `resume`, `model`, `compaction`), `base` (a hash of the prompt without its instruction files) and `instructions` (each instruction file the prompt holds, as `path` and `hash`). An entry of the tree, so a rewind to before it leaves it off the branch. | yes, as the request prefix |
| `user` | `item`: the protocol's user message item (text, attachments by artifact reference, delivery mode). | yes |
| `assistant` | `item`: the protocol's assistant message item (neutral parts, the provider's raw blocks, stop reason, usage, cost), and `request_id`, the provider's id for the request. | yes |
| `tool_result` | `item`: the protocol's tool result item (call id, model-visible content, artifact references, outcome, structured payload, timing). | yes |
| `notice` | `item`: a message appended by the harness: changed instructions, a steering note, a repetition warning. | yes |
| `summary` | `item`: a compaction summary (its `text` is what the model is sent, the carried state included; `covers_through` the last item it summarises), and `carried`, the carried state as data: `plan`, `files` (each `path`, `read`, `changed`, `hash`), `last_user` (the parts) and `artifacts`. Starts an epoch's history; written just before the compaction's `epoch` entry. | yes |
| `attempt` | A failed or abandoned request attempt: the `item` it would have been, the `attempt` number, the `error`, and the partial `parts`. | no |
| `usage` | Usage outside the main loop: `purpose` (compaction, titles) and `usage`. A record. | no |
| `checkpoint` | Which files a tool round changed: `files`, each with `path` (relative to the workspace, or absolute outside it), `before` and `after` (`{hash, bytes}`, or `null` for a file that did not exist; `"kept": false` when the content was too large to keep). `before` can also be `"unknown"`: the change was seen only after it was made (a shell command's) and what the file held could not be recovered. **Only an explicit `null` means "did not exist"**: a missing `before`, or a string this build does not know, reads as `"unknown"`, because undoing a change from "did not exist" removes the file. A build from before `"unknown"` cannot read such a checkpoint, and skips it rather than undo it. The checkpoints of a turn are that turn's snapshot. | no |
| `outcome` | How a turn ended (`ended`, `verification`, `stop_reason`, `error`, `usage`, `duration_ms`, from the turn's `turn.completed`), and in a later record for the same turn, `reverted`: `undone` or `rewound`. A record. | no |
| `meta` | `title`, `labels`, `note`. A later record replaces what it sets. A record. | no |
| `ext` | State saved by an extension: `ext` (its id) and `data`. A record. | no |
| `escalation` | A question waiting for the user, and later its answer. Used by the Coordinator ([17-coordinator.md](17-coordinator.md)), with that page's fields; its `kind` is stored as `category`, because `kind` is the envelope's. Reserved in the first release, and its shape may change before the first use. A record. | no |
| `decision` | Something a Manager session decided without asking, with its reason and the lease clause that allowed it. Reserved like `escalation`. A record. | no |
| `lease` | A lease granted, extended or ended: `event` (`granted`, `extended`, `ended`) and `lease`, its exact terms ([06-permissions-and-sandbox.md](06-permissions-and-sandbox.md)). The standing lease is recorded when a session starts. Task and team leases come after the first release. A record. | no |
| `plan` | The session's plan after a change to it, by the model or by the user: `plan` (the items and the revision). An entry of the tree, so the plan of a branch is the last one on it: a resume gets the plan back, a rewind goes back to the plan of that point, and a fork takes the plan with it. Added in step 13a. **A change by the model's `plan` call is written before the call's result**, because the plan changed when the call ran: a rewind or a fork at the result keeps the plan the call made, and one at the response that made the call does not (since the review of step 13a, which found the entry after the result and a rewind to the result losing it). | no |
| `rewind` | The active position moved to this entry's parent: `reason` (`rewind`, `undo`, `switch`) and `from`, the position before. | no |

**A lease is read strictly.** Every other entry is tolerant. A `lease` record is read through the protocol's strict decoder ([decision 0028](../decisions/0028-enforced-values-fail-closed.md)): exactly `event` and `lease`, an event this build knows, and a lease it understands in full. Anything else refuses the record whole, with the code `lease_not_understood`. **A lease line written in a newer format version is refused too**, never skipped as a line this build cannot read: skipping a newer build's `ended`, or its narrower terms, would leave an older lease in force. So is a damaged line in the middle of the log that holds the JSON string `"lease"`, as the kind or the key of a lease record does: it may have been one. If any lease line of a session is refused, the session still opens, and asking for the lease in force returns that refusal, never a lease: the leases are then unknown, and a lease is never read in part.

**Writing.**

- An entry is one write of one complete line, at the end of the file. The file is opened for writing, not in append mode: on Windows a file opened for appending cannot be cut back, and cutting back is how a failed write is undone. One process writes a session at a time: it holds the session's `lock` file (not a lock on the log, which on Windows would stop other processes reading it). A second writer is refused; it can open the session read-only. On a file system that cannot lock, the session's `lock` and the project's `index.lock` are both taken as no lock, and the work goes on: one writer is then the user's to keep to. The session says so (`Session::is_unlocked`), and since step 13a the core warns the user once, in a notice, when a session's log is being written without its lock.
- **A line is at most 64 MiB**, the most the reader takes as an entry. An entry that would be longer is refused with `session_entry_too_large`, and nothing is written: written, it would be in memory now and skipped as damage, with the branch after it, the next time the log is read. Large content belongs in an artifact.
- The file is created when the first user message is recorded, so an empty session leaves nothing behind. Until then the first entries (the header, a lease, an epoch) are held, and the log is created with all of them in one atomic, owner-only write, so it never exists without its first line. **What the session's store kept meanwhile** (the base state, taken from the start) is removed if the session ends without a prompt: the store then refuses new writes, and whichever comes last, the end of the session or the end of the last write still under way, removes the session's directory. This was chosen over holding the capture back until the log exists, because then every path the store had already handed out would have to move while the capture is still writing. A crash before the first prompt still leaves the directory, without a log, which a listing does not show.
- Durability is a setting, `session.durability`: flush to disk after every item (`item`, the default), at the end of every turn (`turn`), or never (`never`, left to the operating system). The default costs one flush per item and loses at most the item in progress on a crash. Only the user may set it: a project that could choose `never` could cost the user their sessions. **A `lease` record is flushed whatever the setting**, as is a log created with one in it, so that a crash cannot bring back a lease that had ended or been narrowed.
- **If a write fails, the entry is not added to the in-memory session either, and the file is cut back to where it was** (and the cut flushed), so a line that reached the disk does not come back after a crash. Memory never holds entries that are not on disk. If cutting back fails too, the session refuses every later write until it is opened again, which repairs the tail, and its flush at the end of a turn reports that failure rather than success. With `turn`, a flush that fails at the end of a turn is reported and removes nothing: the lines were written, and whether they reach the disk is the operating system's.
- **Ids.** While a session is open, its owner (the agent loop) makes its turn and item ids, starting after the highest in the log (`Log::last_ids`), because it hands out a turn id the moment a prompt is queued and must not wait for the session behind a flush. The store makes item ids only when it repairs: on resume, before the loop starts, and after a rewind or a switch, which report the results they added, each with its call, its item id and its entry (`Repaired`), so that an owner counting its own ids goes on after them.

**Reading.**

- The log is parsed as a stream, and what is kept of each entry is its envelope, the id of the item it holds, and where its line is. The rest of a line is checked and skipped, and read again from the file when it is asked for. A long session therefore costs little memory, and its active branch is read in one pass.
- Unknown kinds and unknown fields are skipped, and kept as they are: a fork copies them. A kind this build does not know stays in the tree, so its children keep their place.
- **A final line that is cut off by a crash is ignored and reported.** A final line with no newline is kept if it is a whole entry: a cut can never turn part of an entry into a different whole one. A damaged line elsewhere is skipped and reported, and an entry whose parent is not an earlier entry starts a branch that stops there, and is reported.
- **Opening a session to read it never changes the file**, whatever it finds: another process may be in the middle of writing a line, which looks exactly like a line a crash cut off. Only a resume, which holds the lock, repairs.
- **Repair on resume.** The bytes of a cut last line are set aside in `log.cut-<offset>`, a private file, and the log is cut back to its last whole line; a missing final newline is added. If the last response on the active branch asked for tools and some have no results (a crash during a tool round), an "interrupted" result is appended for each before anything is sent. A message appended in the middle of the round, a steering note from the user or a notice from the harness, does not end it: the calls before it are still answered. Tools are never re-run automatically. The same repair follows a rewind or a switch to a response that asked for tools.
- The format has a version number in every line. A session whose first line has a newer version than this build opens read-only: it can be read and listed, not written or forked. A format change ships with a migration that reads the old version.

**Large content is stored by reference.** A tool result entry holds only what the model saw. The full output is an artifact. Session logs therefore stay small, and opening a long session stays fast. Other harnesses report session files of hundreds of megabytes where raw tool output is stored inline (see [../reference-notes.md](../reference-notes.md)).

**The index** is a cache: one record per session with id, workspace, title, first prompt, entry and turn counts, the main model, the parent, the log's size, and the created and last-updated times. It is rewritten atomically and owner-only, under `index.lock`, at the end of a turn and when a session is closed, without a flush, because it can be rebuilt. Listing reads it and makes one directory listing of the project: a session the index does not have is read from its log and added, one whose directory is gone is dropped, and an index that is missing, unreadable or of another version is rebuilt from the logs. `--resume` takes a unique prefix of an id.

## The base state

What a session records about the workspace it started in, so that it can be replayed ([16-run-engine.md](16-run-engine.md)). It is taken on a thread of its own after the session starts, never delaying the first prompt, and appended as a `base` record when it is ready. As wired in step 13a: the core starts the capture with the one answer it has about the project's trust and with the permission engine's gate, looks for its result each time something is recorded, and at the end of a session waits up to two seconds for a capture that has not finished. A capture slower than that is let go, and the session has no base state. If the record cannot be written (it is too long for a log line, below), the user is told in a notice that the session cannot be replayed from its start.

- **In a git repository:** the commit (none in a repository with no commits), the branch (none when the head is detached), the workspace's place in the repository, the uncommitted changes to tracked files as a binary patch stored as an artifact (in a repository with no commits, the staged changes and then the unstaged ones), and the untracked files that are not ignored, stored in the checkpoint store: up to 1 MiB a file, 1,000 files and 50 MiB in all, and a patch of up to 50 MiB. A file over the limit for one file is listed as omitted by name, with the reason. Past the limit on the number of files or on bytes in all, one entry, `*`, says so, and nothing after it is kept or listed, so those limits do not make the record grow with the number of files. Files left out for a reason of their own (protected, too large, not a file, unreadable) are still listed one by one; a workspace with millions of those can make a record longer than a log line may be, which is then refused with `session_entry_too_large` and leaves the session without a base state.
- **Links are never followed.** An untracked link is recorded as a link, by the text it holds (`links`: `path` and `target`), and never opened: what it points to may be outside the workspace, or a device that never ends. A directory, a device or a FIFO is listed as omitted with the reason `not_a_file`.
- **The patch needs the whole list of changed files**, because protected files are left out of it by name: every file the patch holds a change to, so in a repository with no commits the staged and the unstaged ones (a file added with `--intent-to-add` is only in the second). If git cannot list them in full, or a protected file's name is not UTF-8 and so cannot be given to git to leave out, no patch is taken, and the record is incomplete, with the reason in its `note`.
- **Outside git:** a listing of the files with their sizes and hashes, up to 20,000 files and 2 seconds, hashing files up to 64 MiB. Their content is not kept, so a replay of such a session needs the files to still match their hashes. Links are not followed.
- **Project trust is an input.** A repository's own configuration can make git run programs: a clean filter runs on `git diff` and `git status`, and an untrusted repository can carry that configuration. For a project that is not trusted only the commit and the branch are read (`git rev-parse` and `git symbolic-ref`, which run nothing of the repository's), and the record is marked incomplete. A capture after the project is trusted appends a second, complete record, which the session's base state then is.
- **What the agent could not read without asking is never kept**, trusted or not, within the caps or not. The capture is given a gate (`KeepGate`: "may the content of this file be kept?"), which the core fills from the permission engine (`Engine::may_store`, step 12): a file is kept when the read rules would let the agent read it unasked. So a file a rule denies or asks about is left out, and so is a file that looks like a secret (`.env`, `*.pem`, a private key; [06-permissions-and-sandbox.md](06-permissions-and-sandbox.md), "Files that look like secrets") unless a rule allows reading it. The level is not part of the answer: nobody approved the base state, so not even `unrestricted` puts a file that looks like a secret in the store. Tracked ones are left out of the patch by name, and every one found is listed as omitted with the reason `protected` (untracked ones only up to the limit on the number of files, past which nothing more is listed).
  - **`cortex-session` has no list of names of its own.** Step 8 gave it one, which also held back ordinary source files (`src/id_map.rs`, through `id_*`) and could disagree with what the `read` tool lets the agent see. The gate is the seam: `cortex-session` cannot see `cortex-policy`, and gains no crate edge.
  - **A file left out because it is outside the workspace makes the record incomplete.** In a workspace below the repository's top, git names the whole repository's changed and untracked files, and the gate refuses those outside the workspace, as a read of them would be asked about. They are not left out by choice, as a protected file in the workspace is, so the record says it is incomplete and how many there were, even where its patch is empty (found by the review of step 12).
  - **A file a tool changed is another matter.** The checkpoint of a round keeps the earlier content of every file a tool changed, a file that looks like a secret included, because undo must put it back exactly. Such an edit happened only after the user approved it or wrote a rule for it, and the store is owner-only.
- **git is run hardened**, and later steps that run git use the same flags (`cortex_session::base::GIT_HARDENING` and `DIFF_FLAGS`): `--no-optional-locks` (git writes nothing it does not have to), `-c core.fsmonitor=false` (no file-system monitor, which a repository's configuration could name as any program), `-c core.quotepath=off`, `-c diff.noprefix=false` and `-c diff.mnemonicPrefix=false`; for a diff also `--no-ext-diff --no-textconv --no-color --no-renames --binary --full-index` with the `a/` and `b/` prefixes, so the patch applies whatever the user's configuration says; and `GIT_TERMINAL_PROMPT=0`, with standard input closed.

## Resume, branches and forks

| Action | What happens |
|---|---|
| Continue (`cortex --continue`) | Opens the most recent session for this workspace. |
| Resume (`cortex --resume <id>`, or the picker) | Opens a chosen session. A unique id prefix is enough. |
| Rewind (TUI) | Moves the active position to an earlier entry, with a `rewind` entry. The next prompt starts a sibling branch from there. Optionally restores files from checkpoints to that point. Each undone turn gets an `outcome` record saying it was rewound. |
| Switch branch (TUI) | Makes another branch active, with a `rewind` entry whose parent is its last entry. Files are not touched. |
| Fork (`cortex --fork <id>`, or a command) | Creates a new session whose log begins with a copy of the active branch (or of the branch up to a chosen entry), line for line, and the session's `base` records, and records where it came from. Leases, outcomes and metadata are not copied: a fork must not inherit a task lease, and records its own standing lease. The artifacts and the checkpoint store are shared by hard links where the file system allows, and copied otherwise. The original is untouched. |

A resumed session continues its epoch, and may get a cache hit, when the harness would build the same prompt but for the instruction files, and the same tools; otherwise it starts a new one ("Context epochs", as built in step 15). Whether the provider's cache has expired does not decide it: a new epoch would drop the history's reasoning for nothing.

## Snapshots and undo

Edits apply without asking ([06-permissions-and-sandbox.md](06-permissions-and-sandbox.md)). That default is only acceptable because every turn can be undone.

- **Per-turn snapshot.** Before any tool writes a file, its previous content is saved in `checkpoints/` under its hash (or the fact that it did not exist), and the round's `checkpoint` entry lists what changed, with what each file was before and what the round left. Together, a turn's checkpoints are its snapshot. Taking one costs a file copy per changed file and nothing when no file changes.
- **How the editing tools reach it** (step 10). `write` and `edit` are in `cortex-tools`, which cannot see this crate, so they record through a seam of their own, `Checkpoints` ([05-tools.md](05-tools.md), "Checkpoints"). The core fills it with the round's `RoundCheckpoint`. A tool hands over the bytes it read, so the core stores them with `DiskStore::put_blob` and records them with `RoundCheckpoint::record_before` (`Before::Absent` for a file that did not exist), and passes what the tool left to `RoundCheckpoint::after`, which it is told for a write that failed as well (the file is then as it was, and drops out of the round). Nothing is read a second time, and the end of a round does not hash a file the editing tools touched: their result is always recorded. The tools do not change a file over the keep limit below, so what they change can always be put back. `crates/cortex-core/tests/it/undo.rs` runs the real tools against a real session this way, with an adapter that step 13 can start from.
- **A file over 16 MiB is not copied.** Its hash and size are recorded, and it is marked as not kept. The files the editing tools change are source files, far smaller; a file over it is generated output, a database or a media file, where a copy per turn costs time and disk for little; and a restore holds the content in memory, which this keeps inside the memory budgets. A rewind lists such files before it starts, as files it cannot put back.
- **Undo** restores the files changed by the last turn and rewinds the session to before it. **Rewind** to any entry does the same back to that point. Both are available from the TUI and the protocol. A rewind is planned first: for each file, what it will be put back to, and whether that is safe.
- A restore checks each file against the state the harness left it in, and does not overwrite something the user has edited since unless the user says so. The check is made again when the rewind is carried out.
- **A checkpoint that cannot be read stops every restore.** A checkpoint of the undone turns that this build cannot read (damaged, or written in a newer format) may have changed any file, including one a readable checkpoint names, so putting the others back could leave a file at the wrong version. The plan lists such checkpoints (`unreadable`), every file is reported as one that cannot be put back, and a rewind moves the conversation without touching a file. A version whose content is no longer in the store is reported the same way, before the rewind.
- **A rewind follows only a plan made for the session where it is.** A plan records the session it was made for and its active position; the rewind refuses a plan for another session or one made before the session moved on, and works out again from the log's own checkpoints what the plan would do, refusing a plan whose target is not on the active branch or that says anything else.
- **Changes made by shell commands** are not captured by file checkpoints. The harness detects them: it compares the workspace's changed-file list before and after each command (through git where there is a repository, otherwise by modification times under the workspace, within a time cap), records what it saw, and saves the previous content of any tracked file the command changed when that content is still recoverable from git. An undo that crosses such a command says exactly which changes it can and cannot restore. The same size limit applies.
- **How a command's changes are recorded.** Each path it changed goes into the round's checkpoint with what is known of its earlier state (`RoundCheckpoint::record_before`): a file the command created did not exist (`null`); a file whose earlier content git still has is stored from that content (`DiskStore::put_stream`); any other changed file is `"unknown"`. A rewind lists an unknown file as one it cannot put back, and never removes or overwrites it, whatever it is now. A file a tool reports changing without saying what it was before is recorded as unknown in the same way.
- **Where a command's changes come from.** The shell tool does the detecting since step 11, and puts what it found in its result's payload, `changes` ([05-tools.md](05-tools.md), "`shell`", "Changed files"). The three kinds of earlier state above are three lists there: a path in `created` did not exist; a path in `restorable` is read from git at `base_commit`; every other path in `modified` or `deleted` is unknown, which is every changed file that had already been changed before the command, and every changed file where git was not asked (no repository, or a project that is not trusted, where a new file cannot be told from a changed one either). The payload also says how the look was made and whether it finished: one that did not finish may have missed files. Turning the payload into the round's checkpoint was wired in step 13a (`cortex-core`, `checkpoints`): the core wraps the shell tool, and when a command is over, folds its `changes` into the same round's checkpoint that the editing tools fill, reading a restorable file's earlier content with `git cat-file blob <base_commit>:./<path>`, which goes through no filter of the repository's. A file that an editing tool and a command both changed in one round keeps the editing tool's record of what it was before, and is looked at again when the round ends for what it is now. The round's `checkpoint` entry is written before the first of the round's results, so that a crash between the two leaves a checkpoint for calls whose results a resume then repairs, never results for changes nobody recorded.
- **Whole-workspace snapshots** (a copy-on-write or shadow-repository snapshot per turn) would make every change undoable at a cost in time and disk on large trees. They are not in the first release. The owner accepted this resolution on 2026-11-12 (conflict C5 in [../build-plan.md](../build-plan.md)).

**Branching time-travel**, forking the conversation and the files together and comparing branches, is not a headline feature. The pieces it needs are here: the log is a tree, each turn has a snapshot, and sessions record their base state.

## What goes into a request

In order, for one request in an epoch:

1. **System prompt** (frozen for the epoch), assembled from fixed sections in a fixed order:
   1. The core instructions: who the agent is and how it works. Short, and ours.
   2. Environment facts that do not change during the session: operating system, shell, workspace root, whether it is a git repository. No date and no clock.
   3. Usage notes contributed by the enabled tools, in tool order.
   4. Project instructions (below).
   5. The project profile: accepted commands, conventions, known flaky tests and facts, inside a token budget ([14-adaptation.md](14-adaptation.md)).
   6. The index of available skills and custom commands, and a one-line summary of each source of extension and MCP tools.
   7. Sections contributed by extensions, ordered by extension id.
   8. The user's appended text, from configuration or a flag.
   A user or project can replace section 1 with their own text. The wording of section 1 can vary by model, as a prompt-style variant ([14-adaptation.md](14-adaptation.md)).
2. **Tool definitions** (frozen for the epoch), in sorted order.
3. **History** for the epoch: the summary if there is one, then every `user`, `assistant`, `tool_result` and `notice` entry on the active branch, unchanged.

The first user message of an epoch also carries what is useful but not stable enough for the system prompt: the current date, and the repository map ([15-efficiency.md](15-efficiency.md)) when it is ready. If the map is not ready in time it follows as an appended notice.

**As built in step 15** (`cortex_agent::context::prompt`):

- **Sections 1, 2, 4 and 8 are written;** 3 (no built-in tool has usage notes beyond its description), 5 (step 17), 6 (steps 28 and 30) and 7 (step 28) are empty and left out. Section 1 is `CORE_INSTRUCTIONS`; section 2 names the operating system, the shell and its version, the workspace and whether it is in a git repository (a `.git` looked for above it, not asked of git); section 8 is `--system-append`, always last. Replacing section 1 from configuration is not built yet.
- **The tools** are the toolbox's, sorted by name, which is the order `cortex-llm`'s strict reduction counts them in.
- **The date** is a text part before what the user wrote, in the epoch's first user message, taken from that message's own `created_at`: so the message is the same bytes whenever it is built, a resume's included, and the stored item is not changed. An epoch that begins with a summary has the date in the summary.
- **A notice is a message in the user's role, and says it is the harness's** ([decision 0034](../decisions/0034-notices-in-the-users-role.md)): its text, and a summary's, is sent after the lead-in `Notice from the harness (Cortex-Harness), not from the user.`, which the core instructions explain. The lead-in is added when the message is built; the log keeps the notice's own text.

## Project instruction files

- **Names.** `AGENTS.md` and `CLAUDE.md`, so people coming from other agents do not have to rewrite anything. When a directory has both, both are read, `AGENTS.md` first. Other names can be added in configuration (`context.instruction_names`).
- **Discovery at the start of an epoch.** The user's own file in the configuration directory first, then one file per directory from the workspace root down to the working directory. All that exist are included, outermost first, each under a header that gives its path.
- **Size.** A total cap (default 48 KiB, `context.instructions_cap`). Beyond it, files are cut from the innermost end with a visible warning in the UI. A warning is never silent truncation.
- **Nested files.** When a tool first touches a file under a directory that has its own instruction file, that file is appended once as a notice.
- **Changes on disk.** Checked at the start of each turn. A changed file is appended as a notice that says it replaces the earlier version. The system prompt itself is not rewritten until the next epoch.

**As built in step 15** (`cortex_agent::context::instructions`, read through the core's `instructions`):

- **The working directory is the workspace root:** the core opens a session in the directory it was started in, so discovery reads the user's files and the root's. Deeper directories are reached as nested files.
- **What is read is held to what the agent could read unasked.** A workspace file is found through the session's path resolver, which follows a link only where it stays inside the workspace (a `CLAUDE.md` that links to `AGENTS.md` is read, once; one that links outside is not), and must pass the permission engine's gate (`Engine::may_store`). In the configuration directory only `AGENTS.md` and `CLAUDE.md` are read. A configured name must be a plain `.md` file name: no separator, no `..`, not hidden ([../security.md](../security.md), section 2).
- **Two names of one file in one directory are read once,** by their content.
- **What the model was given of each file** is the epoch's `instructions` and the notices after it, whose first line names the file in a fixed form (`Instruction file `<path>` changed.`, `is new.`, `was removed.`, `applies to the files under …`), so a resumed or rewound session knows it again with nothing else in the log. A file that appears is told as new, one that goes as removed.
- **Nested files** are looked for once a request, at the safe boundary, under the directories of the files the table of seen files holds.
- **The cut** is marked in the text with the cap; the warning is an `instructions` notice to front ends.
- **Trust.** Instruction files load without project trust, because they are text for the model and cannot grant permissions. Their injection risk is handled in [../security.md](../security.md).

## Budgeting

Before each request the loop estimates the request size.

- **Estimate.** The input and output token counts the provider reported for the last request, plus an estimate for everything appended since (bytes divided by a per-model ratio from the catalog). The provider's counting endpoint is called only when the estimate is within 10% of the limit.
- **Limit.** The model's context window, minus the output reserve (the configured maximum output, capped), minus a safety margin.
- **Trigger.** When the estimate exceeds 85% of the limit, the loop compacts before sending. The ratio is configurable, per model if needed.
- **Fallback.** If a provider still reports a context overflow, the loop compacts and retries once.

**As built in step 15** (`cortex_agent::context::budget`):

- **The ratio of bytes to tokens is measured, not looked up:** each request's content in bytes over the input the provider counted for it, between 1 and 8, and 3 before the first count. The catalog has no such field; a measured ratio follows the model, the language and the kind of content as they are.
- **The counting endpoint is not called yet** ([outstanding](../outstanding/the-token-counting-endpoint-near-the-limit.md)): near the limit the overflow fallback answers a wrong estimate.
- **The limit** is `limit_of(window, max_output)`: the window, less the room for the answer (the role's output limit, or the model's, capped at 32,768 tokens and at a quarter of the window), less a fiftieth of the window.
- **The window** is a local server's report when its probe answered, and otherwise the catalog's ([decision 0035](../decisions/0035-where-the-context-limit-comes-from.md)).
- **After an overflow** the ratio is brought down to what the provider's refusal shows at most (the request's bytes over the window), and the summary request is always cut, to half the limit. A refusal shows only that the request held more tokens than the window, so the true ratio may be lower still: half the limit is the margin. A prompt and tools that are past the trigger on their own are not handled yet ([outstanding](../outstanding/a-prompt-past-the-trigger-on-a-small-window.md)).
- **The thresholds** are `context.compact_at` (0.85) and `context.prepare_at` (0.70), fractions of the limit. The count is the last request's; a new history (a compaction, a new prefix, a reload) starts again from bytes, with the ratio kept.
- **Each request has a context record** (`StatEvent::Context`, before the statistics store of step 16): the estimate by source (system prompt, tools, summary, user, assistant, tool results, notices), the estimate, the limit and the window, what the provider counted, and where the request first differs from the one this process sent before it, across reloads too (`PrefixDifference`: nothing, the settings, the system prompt, the tools, or the message at an index), which on a cache miss says what moved.

## Compaction

Compaction ends the current epoch and starts a new one. It runs between tool rounds, never inside one.

1. **Summarise.** The whole epoch is sent to the model (the session's model, or a configured cheaper one) with the summary instructions. The instructions ask for a fixed outline: the user's goal and constraints, what has been done, decisions and their reasons, the current state of the work, what remains, and any exact text that must survive (names, commands, error messages). The user can add focus instructions to a manual compaction. Extensions can add to the instructions.
2. **Carry state mechanically.** Things that must not depend on a summary's accuracy are copied, not summarised:
   - the plan, from the `plan` tool, including edits the user made;
   - the list of files read and files changed in the session, with their current hashes;
   - the last user message, word for word;
   - references to artifacts mentioned in the last few rounds.
3. **Start the epoch.** Rebuild the system prompt and tool list (re-reading instruction files), then begin the history with one `summary` entry that holds the summary and the carried state.
4. **Recent turns.** By default nothing else is replayed. A setting (`compaction.keep_recent_tokens`, default 0) replays the most recent turns after the summary with their reasoning removed and their text, tool calls and results intact. Replaying them with reasoning intact is not possible on the providers that bind reasoning to history.

The originals stay in the log. Compaction changes what is sent, never what is stored. A compaction can be undone by rewinding to before it.

**What the user sees.** A notice with the token counts before and after, and the summary available to read. Automatic compaction can be turned off, in which case the loop stops and asks when the budget is reached.

**As built in step 15** (`cortex_agent::context::compact`, `turn::epochs`):

- **The summary request** is the epoch's own system prompt, tools and messages, then the summary instructions (`SUMMARY_INSTRUCTIONS`, with the user's focus after them), so that a summary on the same model reads the epoch's cache. It goes to the `fast` role's model when there is one and its window holds the epoch, and otherwise to the main model, at the role's own speed (standard unless set), with at most `16,384` tokens of output. A request too large for the model that summarises is cut from the front, whole turns at a time and without reasoning, after the epoch's summary if it begins with one. After an overflow it is always cut ("Budgeting").
- **The carried state** is the board's plan; the files read and changed; the user's last message (`last_user`); and the artifacts of the last three rounds. The files are what the last summary carried, then what the branch's tool results since say (the file tools' `path` and its kind, and the shell's `changes`, read as the headless report reads them), with the hash this process's table of seen files last saw where it has one. They come from the branch, not from the table alone, because a new process's table is empty and a rewind empties it. The summary item's text is the summary under fixed headings, then the plan, the files read and changed, the user's last message word for word, and the artifacts, after the date.
- **The log gets** a `usage` record for the summary's request, the `summary` entry, then the `epoch` entry, in that order: a crash between the last two leaves an old prompt with a summary-started history, which is valid. Front ends get the summary as an `item.completed`.
- **A summary too large for the new epoch** (with what it carries and replays, past the trigger) is not used: one asked for now, over everything, is tried, and if that is too large too the compaction fails, nothing is recorded, and the turn ends with the error (`compaction_failed`, of kind `context_overflow`).
- **Automatic compaction off** (`context.auto_compact = false`): at the trigger the turn ends with `compaction_needed`, and nothing is sent. The overflow fallback still compacts once ([outstanding](../outstanding/automatic-compaction-off-and-the-overflow-fallback.md)).
- **`session/compact`** compacts an idle session in a turn of its own that sends nothing else, and a running one at its next safe boundary; `focus` is the user's. A turn that has sent its last request has no boundary left, and the compaction waits for the next turn ([outstanding](../outstanding/session-compact-after-a-turns-last-request.md)).
- **`compaction.keep_recent_tokens`** is `context.keep_recent_tokens`; the turns it keeps never begin with a round's results.

### In the background

A compaction that stops the session to write a summary costs the user time. So the summary is prepared before it is needed.

1. When the estimate passes a lower threshold (default 70% of the limit), the loop starts summarising the epoch so far, in the background, on the `fast` model role. The session carries on.
2. When the estimate reaches the compaction trigger, at the next safe boundary, the loop starts the new epoch from that summary. The turns that happened after the summary was taken are replayed after it, with their reasoning removed and their text, tool calls and results intact.
3. If the trigger arrives before the summary is ready, the loop waits for it. This is the only case in which compaction stops the session.

Replaying the newer turns without their reasoning is what makes this valid on providers that bind reasoning to history. The cost is that the model loses its reasoning for those few turns, and one extra summary request is made. If the background summary turns out not to be needed (the session ends first), its tokens were spent for nothing; the lower threshold is set to keep that rare.

**As built in step 15:** the summary is started at a safe boundary before a request, over the epoch as it is then, when `context.background` and `context.auto_compact` are on, and when the ledger has a request for it once the turn's own is taken. It runs beside the turn, and past the turn's end. One that finished has its usage counted at the next boundary. It is used only over a history that still begins as it did, ending with the same item; a change of history (a rewind, a switch of branch) drops it and stops its request, and an interrupt stops one still running. One that failed is not tried again in the background in that epoch: at the trigger a summary is asked for at once, over everything. A summary given up after its request finished is counted at the next boundary; one that finishes when the session has ended, or is stopped while it runs, is not ([outstanding](../outstanding/a-summary-stopped-or-left-is-not-counted.md)). An interrupt of a session whose turn has ended does not reach a summary still running ([outstanding](../outstanding/a-background-summary-past-its-turn-cannot-be-interrupted.md)).

**Provider-side context management.** Some providers can compact or clear old tool results on their side without invalidating reasoning. The design leaves room for a protocol adapter to use those features in place of the steps above, per provider, as a later optimisation. The client-side method works on every provider and is the default.

## Secrets in sessions

- Session logs and artifacts can contain anything a tool printed, including secrets. They are stored with owner-only permissions and never leave the machine on their own.
- A redaction filter runs when entries and artifacts are written. It masks the harness's own credentials by value, and strings that match well-known key formats. It is best-effort and is described as such. `cortex-session` applies it, through its `Redactor` hook, to every string of an entry and to text artifacts line by line as they are written; the filter itself is built in step 13. Within a line of an artifact, each run of valid UTF-8 is redacted on its own: a byte that is not UTF-8 is not text, and is written as it is between the runs, so it never stops the text around it from being redacted. A line that grows past 64 KiB without a newline is redacted in pieces, cut where no character is split. It does not see the provider's own blocks (`raw`), because changing a byte of one makes the provider refuse it on replay, nor the file contents kept for undo, which must be put back exactly, nor artifacts that are not text. The filter is `cortex_base::SecretFilter`, built in step 13a: one pass over the text, about 450 MiB a second ([../performance-budgets.md](../performance-budgets.md), "Data paths").
- **A provider's own block that holds a secret is never written** (the owner's decision for step 13a). Before an assistant message is stored, the filter looks at each of its raw blocks, as the JSON text it is and then string by string with the escapes undone: a key that follows a line break stands after `\n` in the text, and any character may be written as a `\u` escape. If it finds a secret in one, the message is stored as its neutral projection: text and tool calls without their raw blocks, reasoning with its visible text only, provider blocks left out, and nothing that says which provider produced it, so that no protocol ever takes it for something to replay raw. The session that is running keeps the message as it arrived and replays it as before. The user is told, in a notice that does not hold the secret. A request attempt that was given up is stored without raw blocks always: it is kept for debugging and never replayed.
- **An entry the filter changed is marked** (`"redacted": true` in its envelope), and so is a message stored as above. What the log then holds is not what the model was sent, and on the providers that tie each reasoning block to the history before it, a block written after such an entry no longer matches a history read back from the log. So **after a resume, every assistant message from the first marked entry to the end of its context epoch is sent as its neutral projection** (how the mark follows a summary and an epoch, since step 15, is in "What each part of a session's state follows"), as a message from another provider would be ([04-providers.md](04-providers.md), "The conversation model"), and the user is told in one line how many responses that touched. Reasoning from before the first marked entry is replayed as it was. A resumed session without this rule could have its first request refused.
- **A field named `raw` is a provider's block only where a part or a usage record has it.** Under a name the model chose, in a tool call's arguments or in what a tool returned, it is redacted like any other text.
- **The filter is the core's, and a session reads it each time it writes.** A key the core comes to hold while a session runs (a role is moved to another provider) is masked in that session from then on.
- **What is kept exactly, and so can hold a secret:** the checkpoint store. It holds the earlier content of every file a tool changed, and the content of every file `read` showed the model, which is what a changed-only re-read is compared with. Both must be the file's bytes, so neither is redacted. The store is owner-only and belongs to the session.
- `cortex sessions export` applies a stricter pass and shows what it masked. There is no built-in upload or sharing feature.
