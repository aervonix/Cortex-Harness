# Answered in step 13a, on 2026-11-13

Step 13 was split in two so that the core could be reviewed before a front end is built on it. Step 13a built `cortex-core` and the additions to other crates that it needs; step 13b builds `cortex-cli`. These are the choices made with the owner before 13a began, and the ones it put to the owner while it was built. Each of the second kind was accepted as recommended.

## After the review, 2026-11-13

An independent review of step 13a (a read-only second look, by a model that had not seen the step's reasoning, of `main` at `f24c001`) confirmed seven defects, R1 to R7, each with a test that failed on `main`. The fixes were made with each of those tests moved to where it belongs, and the owner chose, through the coordinator, which of its lower-confidence notes to act on.

| Finding or question | What was done | Recorded in |

| **R4. A relative `PATH` entry could make a project's file the shell,** started for its version as soon as a session opened. | **The shell is looked for in the absolute directories of `PATH` only**, and `%ComSpec%` and `%SystemRoot%` are believed only when absolute. A configured `shell.program` given as a relative path is refused. The Windows search is the harness's own: `.exe` and the name as given, never the rest of `PATHEXT`, never the current directory. `shells.json` is keyed by the program's resolved path, as step 13b's record said it was; the program is started by the absolute path it was found at, because a program that is several (`busybox`) reads which to be from its name. | [architecture/05-tools.md](../../architecture/05-tools.md), "Which shell" |
