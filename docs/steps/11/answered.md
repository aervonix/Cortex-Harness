# Answered in step 11, on 2026-11-13

Step 11 built the process runner and the `shell` tool. These are the choices it put to the owner, each accepted as recommended: three before it was built and two with its report.

| Question | The owner's answer, 2026-11-13 | Recorded in |
|---|---|---|
| **Where the operating-system calls for process trees live.** `unsafe` is denied in `cortex-tools`, and no crate with a safe API covers the Ctrl-Break event on Windows, or the session and the death signal on Linux. | **In `cortex-sandbox`,** which may already use `unsafe`, in one small module with a safe API, with a new edge `cortex-tools` to `cortex-sandbox`. The rule about where `unsafe` may be written does not change. | [Decision 0030](../../decisions/0030-process-tree-control-in-cortex-sandbox.md), [architecture/01-workspace.md](../../architecture/01-workspace.md) |
| **What dies on Linux when the harness is killed.** The kernel's death signal reaches the command itself and nothing it started. | **Both the death signal and a guard process:** one small helper for each harness, told every tree's process group, which kills what is left when the harness is gone. It runs in a session of its own and kills only what it was told. | [Decision 0030](../../decisions/0030-process-tree-control-in-cortex-sandbox.md) |
| **What becomes of processes a command leaves running.** The docs said the tool stops waiting and says what happened. | **The call's whole tree is killed when the call ends,** on both OSes, and the result says that the processes were stopped and that background processes are not supported yet. Long-lived background processes are step 54. | [architecture/05-tools.md](../../architecture/05-tools.md), "`shell`" |
| **Whether the look for changed files counts against the budget for starting a command.** Step 11 measured 0.2 ms of overhead for starting a command on Linux, against a budget of 5 ms, and 9.5 ms on a Windows runner, against 30 ms. The look for what the command changed is extra: 2.4 ms in a repository of 500 files on Linux and 73 ms on the Windows runner, growing with the repository. | **It does not.** The budget is for starting the command. The look is reported beside it, with its own cap of half a second a look. | [performance-budgets.md](../../performance-budgets.md), "Latency the harness adds" |
| **One list of the flags git is started with, and one timer.** `cortex-tools` and `cortex-session` each hold a list of the flags, and `cortex-tools` and `cortex-llm` each hold a `Timer` trait, because none of them can see the other. | **Both go in `cortex-base`,** as agreed additions. Step 13 makes the move, where those crates meet; until then each crate keeps its own. | Step 13 |

## Windows CI health, 2026-11-13

A later job looked at why the Windows checks were drifting: tests of `shell::cmd` stopped at their 60 s limit in about one run in seven, and two tiers at or over their budgets. What it found in step 11's own code, and what was decided:

| Found | What was done | Recorded in |
|---|---|---|
| **A command that had exited was counted as a process it left running.** On Windows `Tree::others_running` took the Job Object's count of active processes, less the command while it ran. A job goes on counting a process for a moment after its exit. Asked in that moment it answered 1 for a command that left nothing, and the process runner started the half-second grace for what a command left running. With the real timer that is half a second added to a quick command. On the tests' hand-driven timer the grace never ends: the test was stopped at 60 s. | **Fixed in `cortex-sandbox`,** with the owner's agreement, given through the coordinator, that it restores the intended behaviour: the job is asked for its members by process id, and the ones counted are those that are not the command and have not exited. A command that really leaves a process, detached or not, is counted and killed as before, and tests hold both. A member that cannot be asked whether it has exited is counted as running. | [architecture/05-tools.md](../../architecture/05-tools.md), "`shell`"; `crates/cortex-sandbox/src/tree/windows.rs` |
| **The evidence.** | The trace of a hung test in `windows-try` run 43435383403: exit code 0, the output closed, the job reporting one active process, and the job's one member the command's own process id. A direct test in the same run (start `cmd /c echo`, wait for it, ask) saw the job still list the command in 18 to 62 of 120 exits on a quiet runner. With the old count the new system test fails in 6 of 30 repeats (run 43437537149); with the fix, in none of 30, which is 1,200 exits (run 43437508068). | [ci.md](ci.md) |
| **Why repeating the tests did not show it.** 1,500 repeats of the `cmd.exe` tests alone, and 24 runs of the whole workspace with a line printed between "the command has exited" and the question to the job, had no hang. Printing took longer than the moment lasts. | A trace kept in memory, printed only by a watchdog, caught it. `windows-try` gained a `count` input for repeats, and its page says what a clean repeat does not show. | [testing-and-ci.md](../../testing-and-ci.md), "A Windows run without a pull request" |
| **A call that should end by itself could hang its test.** | The shell tool's test bench bounds such a call, lets every wait go at the bound, and fails the test with the waits the runner was in. | [testing-and-ci.md](../../testing-and-ci.md), "No real waiting in tests" |
