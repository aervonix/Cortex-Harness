| **A repository whose filter must write loses change detection and undo while commands are confined.** The harness's own git runs inside the sandbox with no write root, so a program the repository's configuration names for it runs confined and can change nothing ([decision 0032](../decisions/0032-what-the-linux-sandbox-needs.md), finding 1 of the third review of step 26). A filter that must write to answer — git-lfs's `clean`, which writes its object cache under `.git/lfs` — then fails, and with `filter.lfs.required = true` (what `git lfs install` sets) `git status` fails whenever an LFS-tracked file is dirty. The change list for every command is then incomplete while any LFS file is modified, so no file that command changed is restorable, not only the LFS one; the base state's patch fails too. It is reported honestly (the list says it is incomplete, and why, in the payload and the result), but a repository using git-lfs will hit it. Found by the review of finding 1's route. **Held as a limit for now** (the owner's call): the harness's git stays strictly read-only, and the honest incomplete report stands. **Alternatives, not built:** (a) give the reading git `.git/lfs` as its one write root, only when it is a real directory and reached through no link (finding 6's rule), so LFS works while the git stays off the network — declined for now to keep the git read-only; (b) pass `-c filter.lfs.required=false`, so git falls back to the file's raw content and `status` answers — but the content it then sees for a committed LFS file is the pointer, not the file, so change detection would misread an unchanged pointer as the content and could report false modifications. Also unresolved for whichever option: `cat-file blob` returns the LFS pointer, so an undo would write the pointer back, not the file. | Step 32 (hardening pass) | Before the first release |
