| **A process a command leaves running may change a protected path after the look, and the kill cannot be sure of clearing it.** The tree's end now sweeps the command's session, stopping every member it finds and killing the stopped ones, and keeps sweeping until a long run of empty passes or a bound ([decision 0032](../decisions/0032-what-the-linux-sandbox-needs.md), `tree::unix::kill_session`). That clears an ordinary command's leftovers and a process that forks in a loop more often than not. It cannot promise to: signalling what the process table shows cannot win against a process that forks as fast as it can, and under load a pass can find no live member in the gap between two generations and call the session clear while a child is being born (a false clear: about 1 in 6 at full CPU saturation, measured on the desktop). **What holds until the real fix:** when the kill reaches its bound with the session still alive it reports `escaped`, and the turn stops with a warning that names the watched paths; and, whether or not an escape is reported, the look before every confined command is compared with the look after the last one, and at the session's close against the last look (the continuity check, `cortex-core`'s `SessionSandbox::continuity`), so a protected path a surviving process changes is found by the next command or at close, the turn stops, and the undo is offered — a change the harness's own tools made is told apart and not reported. **The cost of the sweep, and the mitigation the review asked for:** only a deliberate fork bomb reaches the full bound, since an ordinary command clears in well under 200 passes; against one, the full 4,000 passes take about 29 s at some 1,600 processes (7 ms a pass, measured on the desktop), and longer as the bomb fills the table, the bound being by pass count, not wall-clock, so the time grows with how slow each `/proc` scan is under the load the bomb itself makes. A **"kill now" the user has already raised stops the sweep** (`end_until`, which the process runner passes the kill-now interrupt): it gives up at once, reports the tree as escaped, and leaves the rest to the continuity check, so a demand to stop is not made to wait out the bound. What this does not yet do is take the sweep **off the core thread**, so a *fresh* interrupt raised while the sweep is already running — the fork-bomb case — cannot land until the sweep ends: the event loop is still held for that time. Running the sweep on a blocking task was tried and backed out, because adding a blocking-task hop to every command's end shifted the timing of the process runner's own tests; it belongs with the control-group kill of step 32, which removes the sweep altogether. So what is left for the real fix is the certainty and the full freeing of the thread, not the sweep's logic. So detection does not depend on the kill winning; killing for certain does. **Recommendation (must-fix before release):** freeze and kill the whole tree at once with a control group (`cgroup.kill`, Linux 5.14), or a PID namespace where unprivileged user namespaces allow one, so the race cannot be lost and a fork bomb cannot keep forking while the sweep runs; add a detached background sweep after the turn stops and a continuation of the guard's sweep at harness exit, so the sweep never holds the core thread. Note where control groups are not available (WSL without the right cgroup2 mount, some containers, AppArmor-restricted user namespaces on Ubuntu 24.04) and plan a fallback.
