| **An undo after a command whose change list was incomplete does not say what it may have missed.** When the look for what a command changed does not finish — git did not answer within its time cap, git failed or was refused inside the sandbox (a filter that must write), there were more files than one look keeps, or the walk ran out of time — the command's result says the list is incomplete and why (`cortex-tools`'s `Changes::incomplete`, surfaced in the payload and the result text; added by the fixes of step 26). But the round's checkpoint is built only from the lists, and an undo reads only the checkpoint: so an undo of such a turn puts back what the look saw and says nothing about what it may have missed. The gap predates the fixes — it covers the long-standing 500 ms git time cap too — and is only surfaced, not widened, by them. Found by the fixes of step 26. **Recommendation:** carry the incomplete flag and its reason onto the round's `checkpoint` entry (an additive, optional field, so older logs read as complete), and have the rewind's note say, when it is set, that the turn's changes were not fully seen and the undo may not put everything back. **Owner:** the next step that changes the checkpoint entry or the session log; otherwise step 32. | A later step, else step 32 | Before the first release |
